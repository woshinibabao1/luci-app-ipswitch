# 0006 面向"不可信客户端"的三处资源上限

状态：**已实现**（`src/rust/src/httpd.rs`、`switcher.rs`、`main.rs`）
关联：`docs/api.md` 的 `/health`、`/status` 两节

## 背景

本服务把 `0.0.0.0:8790` 敞开在一个**没有鉴权**的端口上，默认配置依赖 OpenWrt
WAN 侧 input 策略拦住外部来源（`main.rs` 启动时会打印这条提醒）。也就是说：
**对面是谁不可知** —— 可能是扫描器、可能是配错了的脚本、也可能是自己写崩的调用方。

原来的实现里，有两条路径会因为这个前提而把路由器拖垮，另有一条让"坏状态"看不见：

1. **请求行没有读取期上限**。`read_until(b'\n', &mut buf)` 会一直往 `buf` 里追加，
   而 `HEADER_TIMEOUT` 约束的是**整次调用**的耗时，不是字节数。所以"客户端每 9 秒
   发 1 字节、始终不发换行"可以让行缓冲一直长下去 —— 读完之后再 `truncate` 已经晚了。

   变异验证时亲眼见到它的形态：把 `take(MAX_LINE)` 去掉后，测试进程直接
   `memory allocation of 17179869184 bytes failed`（要分配 17GB）。路由器只有百来 MB。

2. **写路径没有超时**。客户端连上却不读响应时，socket 发送缓冲写满后 `write_all`
   会一直挂着，那条连接的任务就永久留在那里。

3. **`/health` 只说"进程活着"**。最常见的坏状态恰恰是"服务在跑、AT 后端挂了"——
   那时 `/health` 依旧 200，而每次切换都失败。

## 决定

三条都要有明确上限，且**都不改变切换语义**（切换跑在独立任务里，客户端怎么闹都不
改变设备侧动作）：

| 上限 | 值 | 位置 |
|---|---|---|
| `MAX_LINE` 在**读取期**生效（`reader.take`） | 8192 | `httpd::read_line` |
| `WRITE_TIMEOUT` | 10s | `httpd::handle_switch` 的每条进度写出 |
| `MAX_CONNECTIONS`（信号量） | 32 | `httpd::accept_loop` |

四个具体取舍：

### 1. 上限必须做在读取期，不能"读完再截断"

`take(MAX_LINE as u64)` 把"可读字节数"本身卡死：到上限后 `read_until` 看到 EOF 返回，
`n == 0` 分支把它当"不完整的一行"，直接关掉连接。**代价**是超长行会得到
"连接被关闭"而不是 400 或 414 —— 对这个只服务一个已知调用方的内网端口，
关掉比多写一个状态码更简单，也少一条要维护的分支。

### 2. 连接数用信号量而不是计数器

手写计数器要在每条 `return` 路径上都记得减，漏一处就是永久泄漏；
`Semaphore::try_acquire_owned()` 的 `OwnedSemaphorePermit` 由 Rust 负责在作用域
结束时归还（含 panic 展开）。超出上限时回 **503** 并关闭，而不是让对面干等 ——
干等会让调用方以为服务卡了，503 是可诊断的。

### 3. 写超时按"调用方已走"处理，与主动断开同一条路径

客户端不读、或读得太慢时，超时后只把这条连接标记为 broken（继续排空 channel、
切换照跑），**不取消切换**。这与既有决定一致：换 IP 有副作用，半途停下比跑完更糟
（`httpd.rs` 顶部注释）。

### 4. `/health` 报 503，但**保留** `ipswitchd ok` 前缀

AT 通道探活结果由 `main.rs` 在启动时写入 `Switcher`（`AtomicU8` 三态），
`/health` 与 `/status` 都能读到：

- `Failed` → `/health` 503 + `"status":"degraded"`；
- `Ok` / `Unknown` → 200。

`Unknown`（还没探过）**不算失败**：启动探活失败并不阻止服务启动（后端可能稍后就绪），
所以"没探过"不等于"干不了活"。

★ 兼容性：响应体仍然是 `ipswitchd ok` **开头**，只在后面补一行 JSON。
`docs/api.md` 里既有的契约就是 `grep "ipswitchd ok"` 判活，改成纯 JSON 会让既有脚本
静默失效 —— 那是比"多一行 JSON"严重得多的破坏。

## 考虑过的替代

- **在 socket 层量"读了多少字节"来做测试**：测不出来。实测客户端往一条不发换行的
  请求里灌 4MB 也会「成功」—— 因为服务端虽然停止读取，字节全堆在内核收发缓冲里。
  所以这条守卫只能在 `read_line` 上量（`read_line_is_bounded_by_max_line`）。
- **超长行回 414 URI Too Long**：要先把行读完才知道超长，而"读完"正是要避免的事。
  用 `take` 的代价就是只能以"关连接"收场。
- **`/health` 返回纯 JSON**：破坏既有脚本，见上。
- **给 `MAX_CONNECTIONS` 之外的连接排队等待**：那等于把缓冲从连接挪到 accept 队列，
  总量并没有上限。503 是诚实的。
- **在 `/status` 里把 AT 探针的超时也调短**：留待观察。`/status` 会真的下发一条
  `AT^NDISSTATQRY?`（读命令，只读），最坏要等 `RPC_TIMEOUT`(25s)；缩短它会引入
  "通道忙时误报读不出来"的风险，而它的定位是人工排查工具，不是高频探针。

## 后果

- 新增 3 个上限 + 1 个 AT 状态字段，`docs/api.md` 的 `/health`、`/status` 已同步。
- release 体积：**595,968 → 605,696 字节**（+9.7KB；`opt-level="s"` + `lto` 下这属于
  serde_json 那行 JSON 与信号量代码的代价）。
- 测试：48 → **59** 条（新增 6 条端到端 + 5 条尾注单元用例）。

## 已知未覆盖（如实说明）

`WRITE_TIMEOUT` **没有判别性用例**。它守的是"客户端不读、且进度多到把发送缓冲写满"
这个组合，而一次切换只产生几 KB 进度、远小于 socket 缓冲；要造出这个场景得让假后端
回一个几 MB 的 `AT^NDISSTATQRY?` 应答，那已经不是真机形态了。

现有用例（`client_that_never_reads_does_not_hold_the_connection_task`）验的是
"这条连接之后服务端仍能正常服务"，它在**去掉写超时时也照样通过** —— 所以它守不住
这一行。这一处目前靠代码注释与人工审查守着：**改这一段请手工推演一遍"客户端持续
不读"的情形**。
